# Roadmap

This is a direction for the project, not a promise of dates or completed
features. Each section states what sindook must deliver for the people
who rely on it; the order is deliberate.

Sindook's funding model is the one used by established open-source
security products: the CLI, the Go library, and the file format stay
free and open under Apache-2.0, permanently; organizations that depend
on sindook fund continued development through support and services.

## Where sindook is (v0.11.1)

The cryptographic core and the release engineering are in place: hybrid
X-Wing recipients, the public `box` and `xwing` Go APIs, sixteen fuzz
targets under daily ClusterFuzzLite runs, reproducible signed releases
with SBOMs and provenance, and a per-release compatibility fixture
chain. On top of that sit the working verbs: seal, open, verify with
baselines and concurrency, inspect, rewrap, rotate for retiring an
identity across many files, scan for crypto posture, contacts, and
diagnostics. What follows is the direction for turning a sound engine
into a daily tool.

## Near term — the daily driver

Make sindook usable under pressure by someone who reads nothing and
scripts everything.

- One directory contract. `seal`, `open`, and `verify` accept directory
  operands and walk them the way `rotate` already does: recursive,
  deterministic order, a per-file status report, a summary line, the
  same exit codes, and `-json` parity. A half-sealed folder finishes
  instead of double-sealing; originals are never destroyed
  automatically.
- A folder as one artifact. `seal DIR -o bundle.sindook` packs and seals
  a whole tree into a single file, and `open` restores it, with no tar
  requirement and with extraction that refuses path traversal. For
  handoffs and archives, one file to move beats a tree of them.
- Honest time control. Expiry can be stored as metadata that `inspect`
  shows and `open` warns about after the date passes; it is information,
  not enforcement, and the documentation says so. Real destruction on a
  schedule remains what it is today: seal to a dedicated identity and
  destroy that identity.
- Proof infrastructure: a benchmark table regenerated by script, a
  coverage floor enforced in CI, and recipes for the professional loops
  (nightly backup verification, evidence handoff, offboarding, timed
  access).

## v1.0 — The long-term promise

Earn the trust that decades-long storage requires.

- An independent security audit of the file format, key management,
  and X-Wing construction, funded and published.
- A frozen, documented file format with an explicit compatibility
  contract and enforced fixtures across every released version.
- An exercised security-response process: private reporting, response
  timelines, and at least one coordinated disclosure cycle.
- Stable CLI and Go API commitments, as described in
  docs/COMPATIBILITY.md.

## v1.x — Team operations

Serve the workflows of teams and organizations with long-lived data.

- Key IDs in the file format, following docs/KEYIDS_DESIGN.md: inventory
  without private keys, rotation selected by metadata, partial slot
  surgery — after the 1.0 format freeze, with the privacy trade-offs
  that document states.
- Team key directories: shared recipient lists that stay in sync
  without trading private keys.
- Machine-readable `verify` and rotation reports for backup-compliance
  jobs, and rotation-due awareness so rewrap happens before people
  leave.
- A desktop application for people who should not need a terminal; the
  CLI remains fully supported and free.

## Beyond

- Additional recipient or provenance mechanisms, only with format
  compatibility and security review.
- Hardware-backed identity integrations where platform APIs provide a
  suitable security boundary.
- More package-manager distribution options once release verification
  is repeatable.

Sindook will not add new cryptographic primitives or incompatible file
formats merely for feature breadth. It will not pretend that software
can enforce time limits on data whose keys you hold, and it will not
move your files into a managed store: the sealed file is the artifact,
and it must outlive any tool. Security, interoperability, and long-term
file readability take priority.
